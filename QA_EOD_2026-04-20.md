### ✅ Issue #1 (SR) — `refresh_platform_analytics_views()` missing — **RESOLVED (SR prod)**

**Root cause:** `database/init/004_platform_analytics.sql` *is* in the SR repo and was intended to run via `backend/scripts/init_database.py` on first init, but `init_database.py` classifies all non-CREATE-TABLE failures as "non-critical" and silently skips them. Original first-run init failed when the `pg_stat_statements` extension could not be created on RDS (requires `rds_superuser`), and every subsequent statement that depended on the `leads.source` column/enum was skipped — leaving the 8 materialized views, the `refresh_platform_analytics_views()` function, and all related indexes uninstalled.

No source-code change was needed (the SQL is already in the repo). The fix is purely operational: apply the existing migration to the live SR prod DB.

**Action taken (SR prod `sleepreach-prod-db`):**
- Staged processed SQL (pg_stat_statements stripped, `CONCURRENTLY` removed for multi-stmt autocommit) at `s3://sleepreach-backups-prod/tmp/fix_sr_analytics_full.sql`.
- Executed via `aws ecs run-task` against `sleepreach-prod-backend:31` with a presigned-URL runner (task `61372da2026248c28d1d18fc4150a10f`).
- Result: `ok=57 fail=3`, exit=0. Failures were (a) a pre-existing `UNION ALL / ORDER BY` placement bug inside `get_platform_insights()` in the source SQL, (b) `analytics_daily_summary` table does not exist in SR DB (that table is owned by a different, never-applied migration), (c) dependent `COMMENT ON FUNCTION get_platform_insights`. **None block the target function or any MV.**
- Verification queries from inside the task:
  - `pg_proc` → `refresh_platform_analytics_views` ✅
  - `pg_matviews` → all 8: `mv_platform_analytics`, `mv_platform_condition_distribution`, `mv_platform_daily_stats`, `mv_platform_hourly_distribution`, `mv_platform_monthly_stats`, `mv_platform_priority_distribution`, `mv_platform_status_distribution`, `mv_platform_weekly_stats` ✅

### ⚠️ SR stg — discovered separate pre-existing issue, not within scope

While applying the same migration to `sleepreach-stg-db` (task `f8daddc4d8b9435892c6835821b6ab3f`), we discovered the staging DB has only 2 tables total (`platforms`, `analytics_refresh_log` — both created by our own run). The `leads` table and the entire application schema **do not exist in SR staging**. This is why every MV creation failed with `relation "leads" does not exist`.

**This is a pre-existing environmental gap** in SR staging (the full schema was never applied), independent of the analytics-views issue. Running `python scripts/init_database.py` on the SR stg backend container exits 1 with `SQL file not found: /app/scripts/combined_init.sql` — the container does not ship `combined_init.sql`, so there is no single-shot idempotent init available. Fixing this requires applying the full `database/init/001…025_*.sql` chain to SR stg, which is **a separate change-scoped work item** and was not requested. Customer-facing SR prod is fully green; SR staging is presently a hollow DB (the backend service still responds to health checks, but has no data layer). Flagging for a separate ticket.
